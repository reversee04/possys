MRA EIS API INTEGRATION GUIDE
For a C# / .NET Retail POS Application

Version: 1.0
Date: 25 August 2026

======================================================================
1. PURPOSE OF THIS GUIDE
======================================================================

This guide explains how to integrate a Retail POS application with the
Malawi Revenue Authority (MRA) Electronic Invoicing System (EIS) API.

The guide is based on the EIS workflow and endpoint descriptions provided
for this project. It focuses on a C#/.NET POS application using:

- C#
- .NET / ASP.NET Core concepts
- Entity Framework Core
- HTTP/REST APIs
- JSON
- A local database such as SQLite or SQL Server

IMPORTANT:
The endpoint names, URLs, request fields, response fields, HTTP methods,
headers, authentication rules, error codes, and cryptographic/QR
algorithms must be taken from the official MRA EIS API documentation.
Where this guide gives example C# classes or pseudocode, those examples
are architectural examples and must be adjusted to the exact MRA schema.

3. MAIN EIS MODULES
======================================================================

The EIS API can be understood as four major groups.

3.1 ONBOARDING

Used when a terminal is activated for the first time.

Main operations:

- Terminal Activation
- Terminal Activated Confirmation

The Terminal Activation Code (TAC) is entered by the taxpayer/user.
The POS sends it to MRA. MRA validates it and returns the terminal's
initial configuration.

The POS must save that configuration locally before confirming activation.

After confirmation, the TAC expires and should not be used again.

--------------------------------------------------

3.2 CONFIGURATION

Used to retrieve the latest configuration from MRA.

The configuration contains three important areas:

A. Global configuration
   - Tax rates
   - MRA-controlled global settings
   - Other global parameters

B. Terminal configuration
   - Terminal label
   - Active status
   - Trading name
   - Email
   - Phone
   - Address
   - Terminal site
   - Offline transaction limits

C. Taxpayer configuration
   - TIN
   - VAT registration status
   - Tax office
   - Activated tax rates
   - Levies

The POS should retrieve configuration:

- At terminal startup/restart
- At the beginning of the business day
- When MRA indicates that configuration has changed
- At any additional interval required by the official specification

--------------------------------------------------

3.3 SALES

The sales module has three main operations:

1. Submit Sales Transaction
2. Last Submitted Online Transaction
3. Last Submitted Offline Transaction

Every receipt generated during normal online operation must be
submitted to MRA according to the EIS requirements.

MRA returns an invoice validation signature/data that must be handled
according to the official specification and represented as the required
QR code on the receipt.

For certified offline terminals, eligible transactions can be queued
locally and submitted later when connectivity is restored.

--------------------------------------------------

3.4 UTILITIES

The provided utility endpoints are:

1. Ping
2. Product Status
3. Taxpayer Initial Inventory Upload
4. Get Terminal Site or Branch Products and Services
5. VAT 5 Certificate Validation
6. Get Terminal Blocking Message
7. Check Terminal Unblock Status

These should be implemented as separate services rather than mixed into
the sales code.

5. CONFIGURE THE MRA API
======================================================================

Put the MRA EIS base URL in configuration instead of hardcoding it
throughout the application.

Example appsettings.json:

{
  "EIS": {
    "BaseUrl": "https://eis-api.mra.mw"
  }
}

The exact production/test environment URL should be confirmed from MRA.

If separate test and production environments are supplied, configure
them separately.

Example:

{
  "EIS": {
    "BaseUrl": "...",
    "Environment": "Test"
  }
}

Never commit terminal secrets or security keys into source control.

======================================================================
6. CREATE THE EIS API CLIENT
======================================================================

Create:

Services/EIS/EISApiClient.cs

The API client should be responsible for:

- Creating HTTP requests
- Adding authorization
- Sending requests
- Reading HTTP responses
- Deserializing JSON
- Handling common API errors
- Logging useful technical information

Example architecture:

public class EISApiClient
{
    private readonly HttpClient _httpClient;

    public EISApiClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }
}

Do not place all endpoint-specific business logic inside this class.

Instead:

TerminalActivationService
ConfigurationService
EISSalesService
ProductStatusService

should use the API client.

7. TERMINAL ONBOARDING / ACTIVATION
======================================================================

The onboarding process begins when a taxpayer obtains a Terminal
Activation Code (TAC) from the MRA EIS Portal.

The user enters the TAC into the POS.

Flow:

    User enters TAC
          |
          v
    POS activation screen
          |
          v
    TerminalActivationService
          |
          v
    EISApiClient
          |
          v
    MRA Terminal Activation Endpoint
          |
          v
    MRA validates TAC
          |
          v
    Configuration returned
          |
          v
    POS saves configuration
          |
          v
    POS sends activation confirmation
          |
          v
    MRA flags terminal as activated

CRITICAL RULE:

Do not send the activation confirmation before the returned
configuration has been successfully persisted locally.

If saving the configuration fails, do not tell the user that activation
is complete.

======================================================================
11. ACTIVATION CONFIRMATION
======================================================================

After successfully saving the configuration:

    Save configuration
          |
          v
    Verify save succeeded
          |
          v
    Send activation confirmation
          |
          v
    MRA marks terminal activated
          |
          v
    Store local activated state
          |
          v
    Display "Terminal successfully activated"

If confirmation fails, the POS should not incorrectly show the terminal
as fully activated.

The activation process should be retryable where the MRA specification
allows it.

Because the TAC expires after successful confirmation, do not create
logic that repeatedly submits the same TAC without understanding the
actual activation state.

======================================================================
12. GET LATEST CONFIGURATION
======================================================================

Once activated, the terminal must keep its configuration current.

The documentation says Get Latest Configuration should be called:

- When the terminal starts/restarts
- At the beginning of the business day
- When a sale response indicates that configuration has changed

The response contains:

globalConfiguration
terminalConfiguration
taxpayerConfiguration

Example response structure:

{
  "statusCode": 0,
  "remark": "string",
  "data": {
    "globalConfiguration": {
      "id": 0,
      "versionNo": 0,
      "taxrates": []
    },
    "terminalConfiguration": {
      "versionNo": 0,
      "terminalLabel": "string",
      "isActiveTerminal": true,
      "emailAddress": "string",
      "phoneNumber": "string",
      "tradingName": "string",
      "addressLines": [],
      "terminalSite": {},
      "offlineLimit": {}
    },
    "taxpayerConfiguration": {
      "versionNo": 0,
      "tin": "string",
      "isVATRegistered": true,
      "taxOfficeCode": "string",
      "taxOffice": {},
      "activatedTaxRateIds": [],
      "activatedTaxrates": [],
      "activatedLevies": []
    }
  }
}

The exact response model should match the official API documentation.

======================================================================
13. CONFIGURATION VERSIONING
======================================================================

Store version numbers locally.

For example:

Global configuration version:    5
Terminal configuration version:  3
Taxpayer configuration version: 7

After Get Latest Configuration:

Global configuration version:    6
Terminal configuration version:  3
Taxpayer configuration version: 7

The POS should replace/update the relevant configuration.

Do not assume tax rates are permanently fixed.

MRA may change configuration, and the POS must apply the latest valid
configuration.

======================================================================
14. SHOULD DOWNLOAD LATEST CONFIG
======================================================================

After submitting a sale, the MRA response may indicate:

shouldDownloadLatestConfig = true

This means the POS must call Get Latest Configuration.

Flow:

    Submit Sale
        |
        v
    MRA response
        |
        v
    shouldDownloadLatestConfig?
        |
       YES
        |
        v
    Get Latest Configuration
        |
        v
    Save configuration
        |
        v
    Continue operating

This flag must not be ignored.

======================================================================

The sales module contains:

1. Submit Sales Transaction
2. Last Submitted Online Transaction
3. Last Submitted Offline Transaction

The normal online sales flow is:

    Customer buys products
          |
          v
    POS calculates transaction
          |
          v
    Save local sale
          |
          v
    Submit sale to MRA
          |
          v
    Receive MRA response
          |
          v
    Process invoice validation information
          |
          v
    Generate required QR representation
          |

Example:

    Created
    Pending
    Submitted
    Failed
    Offline
    Syncing
    Synced

======================================================================
16. WHY SAVE THE SALE LOCALLY FIRST?
======================================================================

A power failure or application crash can happen during communication.

Example:

    POS sends invoice
          |
          v
    MRA receives invoice
          |
          X
    POS crashes before receiving response

The POS cannot simply assume the invoice failed.

This is why the Last Submitted Online Transaction endpoint is useful.

A robust flow is:

    Save sale locally
          |
          v
    Submit to MRA
          |
          v
    Response received?
       /       \
     YES        NO
      |          |
      v          v
   Process     Reconcile
   response    before retrying

Do not blindly submit a duplicate invoice when the result is uncertain.

======================================================================
19. QR CODE GENERATION
======================================================================

For online transactions:

    MRA sale response
          |
          v
    Invoice validation information
          |
          v
    POS converts it according to MRA specification
          |
          v
    QR Code
          |
          v
    Receipt

Do not invent the QR payload format.

Use the exact data/encoding requirements provided by MRA.

For offline-certified terminals, MRA provides a lightweight mechanism
using terminal-specific security material. The exact algorithm and key
handling must be implemented exactly as specified by MRA.

Never replace the required MRA mechanism with a random QR code, simple
Base64 encoding, or an arbitrary hash.

20. OFFLINE SALES
======================================================================

Offline functionality is only for terminals certified/allowed by MRA.

When connectivity is unavailable:

    Sale
      |
      v
    MRA request fails
      |
      v
    Check whether terminal is allowed to operate offline
      |
      v
    Check offline limits
      |
      +----------------------------+
      |                            |
      v                            v
    Allowed                    Not allowed
      |                            |
      v                            v
    Queue transaction          Stop/handle
      |                        according to
      v                        MRA rules
    Generate required
    offline validation data
      |
      v
    Print receipt

Do not assume that any API failure automatically authorizes offline
sales.

Conceptually:

    Can transaction go offline?

             |

             |
             v
    Transaction within age limit?
             |
             v
    Cumulative offline amount

26. PING UTILITY
======================================================================

Ping is a health-check endpoint.

It can be used to determine whether the MRA API is reachable and
responsive.

Example:

    POS
     |
     v
    Ping
     |
     +---- Success ----> MRA available
     |
     +---- Failure ----> MRA unavailable

Use it for:

- Startup health checks
- Dashboard status
- Monitoring
- Offline queue processing
- Troubleshooting

Example dashboard:

    MRA EIS
    --------------------
    API:       ONLINE
    Terminal:  ACTIVE
    Config:    CURRENT
    Queue:     0
    --------------------

IMPORTANT:

A successful Ping does not guarantee that a subsequent sale request
will succeed. Connectivity can change between requests.

    POS startup
       |

34. HANDLING POWER FAILURE / CRASH
======================================================================

A common real-world problem is:

    1. POS creates invoice
    2. POS sends request
    3. MRA receives request
    4. POS loses power
    5. POS never receives response

When the POS restarts:

    Load incomplete local transactions
             |
             v
    Identify uncertain transactions
             |
             v
    Query Last Submitted Online Transaction
             |
             v
    Compare response
             |
       +-----+------+
       |            |
     Found        Not found
       |            |
       v            v
    Mark as       Follow official
    submitted     retry/reconciliation
                  rules
             |
             v
         Continue

This is safer than simply resending everything.

======================================================================
36. ERROR HANDLING
======================================================================

Your EIS integration must distinguish between:

A. Network errors
   - Internet unavailable
   - Timeout
   - DNS failure
   - Connection reset

B. HTTP errors
   - 400
   - 401
   - 403
   - 404
   - 500
   - etc.

C. MRA business errors
   - Invalid data
   - Invalid TAC
   - Invalid configuration
   - Invalid tax information
   - Terminal not active
   - Other EIS-specific errors

D. Local errors
   - Database unavailable
   - Failed configuration save
   - QR generation error
   - Receipt printer error

Do not treat all errors as "offline".

For example:

    Invalid sale data
          !=
    Internet unavailable

An invalid sale should not automatically be placed into the offline
queue.

======================================================================
38. SECURITY
======================================================================

Security is extremely important because the terminal receives
authentication/security information from MRA.

Follow these rules:

1. Use HTTPS.
2. Do not hardcode credentials.
3. Do not store secrets in Git.
4. Do not display security keys in the UI.
5. Protect local configuration.
6. Restrict access to the terminal database.
7. Log operations without logging sensitive secrets.
8. Use the exact MRA authentication mechanism.
9. Follow MRA's key-management requirements.
10. Do not invent cryptographic algorithms.

For a production POS, consider protected OS storage or another
appropriate secure secret-storage mechanism for sensitive material,
subject to MRA's requirements.

43. WHY INTERFACES ARE USEFUL
======================================================================

Instead of:

    EISSalesService

you can define:

    IEISSalesService

and implement:

    EISSalesService : IEISSalesService

This helps with:

- Testing
- Dependency injection
- Replacing implementations
- Cleaner architecture

Example:

public interface IEISSalesService
{
    Task SubmitSaleAsync(int saleId);
}

Then:

public class EISSalesService : IEISSalesService
{
    public async Task SubmitSaleAsync(int saleId)
    {
        // implementation
    }
}

47. COMMON MISTAKES TO AVOID
======================================================================

1. Hardcoding MRA URLs everywhere.

2. Sending activation confirmation before saving configuration.

3. Storing the TAC as if it were a permanent credential.

4. Ignoring configuration versions.

5. Ignoring shouldDownloadLatestConfig.

6. Treating every API failure as permission to sell offline.

7. Inventing an offline QR algorithm.

8. Inventing a QR payload format.

9. Logging terminal security keys.

10. Sending duplicate transactions after an uncertain response.

11. Deleting transaction records immediately after successful submission.

12. Putting all API code inside XAML code-behind.

13. Using the POS database model directly as the MRA request model.

14. Hardcoding MRA tax rates.

15. Assuming a successful Ping guarantees every subsequent request will
    succeed.

53. FINAL NOTES
======================================================================

The MRA EIS integration is not just a single API call. It is a complete
terminal lifecycle consisting of:

    ONBOARDING
       |
       v
    CONFIGURATION
       |
       v
    SALES
       |
       v
    QR / RECEIPT
       |
       v
    OFFLINE QUEUE
       |
       v
    SYNCHRONIZATION
       |
       v
    RECONCILIATION
       |
       v
    COMPLIANCE / UTILITIES

The most important engineering principle is to keep MRA integration
separate from the POS user interface.

Build the integration as services, use DTOs for MRA requests/responses,
use Entity Framework Core for persistent local data, and maintain a
clear transaction state so that power failures, network failures,
configuration changes, and duplicate submissions can be handled safely.

For the exact endpoint implementation, always use the official MRA EIS
documentation as the source of truth for:

- Endpoint paths
- HTTP methods
- Request schemas
- Response schemas
- Authorization headers
- Required fields
- Error codes
- Validation rules
- QR format
- Offline algorithm
- Security/key handling
- Transaction sequencing
- Retry rules
- Terminal blocking rules
